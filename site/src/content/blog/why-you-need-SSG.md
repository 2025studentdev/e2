在 Web 开发里，渲染策略的选择往往比框架本身更重要。SSG（Static Site Generation，静态站点生成）不是新概念，但随着 Astro、Next.js、Nuxt、Hugo 等工具的成熟，它重新成为内容型网站的首选方案。原因很简单：大多数网站的内容并不需要每次请求都重新生成，却要服务大量读者。把生成工作提前到构建时，是让网站更快、更稳、更便宜的最直接方式。

## SSG 到底是什么？

SSG 的核心思想是：在构建阶段就把页面渲染成完整的 HTML 文件，而不是等到用户请求时才在服务器上生成，也不是完全交给浏览器用 JavaScript 渲染。

构建完成后，你会得到一堆静态文件：HTML、CSS、JavaScript、图片等。它们可以被直接部署到 CDN、对象存储或任何静态托管服务上。用户访问时，CDN 边缘节点直接返回预先生成的 HTML，不需要查询数据库，也不需要执行服务端逻辑。

这和另外两种常见模式形成对比：

- SSR（服务端渲染）：每次请求到达服务器时，实时生成 HTML。
- CSR（客户端渲染）：先返回一个空壳 HTML，再由浏览器下载 JavaScript 并渲染页面。

SSG 把“渲染”这个动作从运行时挪到了构建时，从而把运行时复杂度降到了最低。

## 为什么你需要 SSG？

### 1. 性能：预生成的 HTML 天然更快

SSG 页面不需要等待服务器查询数据库或调用 API。CDN 可以直接从边缘节点返回缓存好的 HTML，TTFB（首字节时间）通常只有几十毫秒。浏览器拿到 HTML 后就能立即渲染首屏，LCP（最大内容绘制）和 CLS（累积布局偏移）也更容易做好。

对于内容型网站，这种性能优势非常明显。即使流量暴涨，静态文件也不会变慢，CDN 只是多返回几份相同的文件而已。

### 2. 安全：没有运行时，就没有运行时漏洞

SSG 部署后通常没有 Node.js 进程、没有数据库连接、没有服务端会话。攻击面大幅缩小。你不用担心 SQL 注入、服务端模板注入、依赖漏洞被远程利用等问题。静态文件本身也很难被篡改，除非你的构建流程或托管平台被入侵。

### 3. 成本与可扩展性：便宜到几乎免费

静态文件可以托管在 Cloudflare Pages、GitHub Pages、Netlify、Vercel 等平台上，免费额度通常足够个人项目使用。即使流量很大，CDN 的成本也远低于运行服务器和数据库。遇到突发流量时，静态站点几乎不会崩溃，因为它不需要为每个请求消耗计算资源。

### 4. SEO 与可访问性：内容就在 HTML 里

搜索引擎爬虫和社交平台抓取器更擅长处理完整的 HTML。SSG 页面在首次响应中就包含全部内容，不依赖 JavaScript 执行。这对 SEO 更友好，也让禁用 JavaScript 或使用老旧设备的用户能够正常阅读内容。

### 5. 可靠性：没有服务器，就没有服务器宕机

SSG 站点没有运行时服务器需要维护。CDN 本身具备高可用性和冗余。只要构建产物没问题，网站就能持续访问。你不需要半夜起来重启服务，也不需要担心数据库连接池耗尽。

### 6. 开发体验：内容与代码分离，Git 工作流

SSG 通常与 Markdown、MDX 或 Headless CMS 配合使用。内容以文件形式存在，可以走 Git 工作流：分支、Pull Request、预览部署、回滚。开发者用组件化方式写布局，内容作者用 Markdown 写文章，职责清晰。

## SSG、SSR、CSR 对比

| 维度 | SSG | SSR | CSR |
|---|---|---|---|
| 渲染时机 | 构建时 | 每次请求 | 浏览器运行时 |
| 首屏速度 | 极快 | 较快 | 较慢 |
| SEO | 很好 | 很好 | 需要额外处理 |
| 服务器成本 | 极低 | 较高 | 低 |
| 动态能力 | 弱，需额外方案 | 强 | 强 |
| 适用场景 | 博客、文档、营销页 | 个性化页面、电商 | 后台系统、SPA |

## 什么时候该用 SSG？

SSG 特别适合以下场景：

- 博客、个人网站、作品集
- 文档站、知识库、帮助中心
- 营销落地页、产品介绍页
- 电商产品详情页（价格和库存变化不频繁）
- 任何内容更新频率低于访问频率的网站

这些场景的共同点是：内容相对稳定，但访问量可能很大。预生成能带来最大的收益。

## 什么时候不该用 SSG？

SSG 不是万能药。以下场景需要谨慎：

- 高度个性化的仪表盘，每个用户看到的内容都不同
- 实时聊天、协作编辑、股票行情
- 需要登录后才能访问的动态内容
- 内容每秒都在变化，且不能接受构建延迟

不过，现代 SSG 框架已经支持混合渲染。你可以在静态站点中嵌入动态岛屿、边缘函数或按需重新验证，不必完全放弃 SSG。

## 现代 SSG 已经进化

今天的 SSG 不再是“纯静态”的代名词。主流框架提供了多种混合能力：

- 增量静态再生成（ISR）：在后台按需重新生成页面，用户仍然访问静态版本。Next.js 的 `revalidate` 是典型例子。
- 按需重新验证：内容更新时，通过 Webhook 触发特定页面重新构建。
- 岛屿架构：页面大部分是静态 HTML，只有交互组件在客户端水合。Astro 是代表。
- 边缘函数：在 CDN 边缘运行少量动态逻辑，处理表单、鉴权或 A/B 测试。

例如，在 Next.js 中可以这样配置增量再生成：

```js
export async function getStaticProps() {
  const posts = await getPosts();
  return {
    props: { posts },
    revalidate: 60,
  };
}
```

页面首次构建后，每 60 秒最多在后台重新生成一次。用户始终拿到静态 HTML，但内容不会永远停留在构建那一刻。

## 工具选择参考

| 工具 | 特点 | 适合 |
|---|---|---|
| Astro | 默认零 JS，岛屿架构，内容集合 | 博客、文档、内容站 |
| Next.js | React 生态，ISR、SSR、SSG 混合 | 全栈 React 项目 |
| Nuxt | Vue 生态，混合渲染 | Vue 项目 |
| Hugo | 构建极快，Go 模板 | 纯静态博客、文档 |
| Eleventy | 简单灵活，多模板语言 | 轻量静态站 |
| Gatsby | React + GraphQL | 内容型 React 站点 |

选择时优先考虑团队熟悉的技术栈，以及项目是否需要混合渲染能力。

## 常见误区

SSG 不等于没有 JavaScript。你仍然可以在静态页面中使用 React、Vue 或原生 JS 添加交互，只是首屏内容不依赖 JS。

构建时间会随页面数量增长。大型站点可能需要增量构建或分布式构建。Hugo 这类工具在构建速度上有明显优势。

内容更新需要重新构建。如果每次改一篇文章都要等几分钟，体验可能不好。ISR 或按需构建可以缓解这个问题。

动态功能需要额外方案。评论、搜索、表单提交等功能不能只靠静态文件，通常需要第三方服务、边缘函数或 API。

## 结论

如果你在做内容型网站，SSG 应该是默认选择。它把复杂度推到构建时，让运行时尽可能简单。用户得到更快的页面，开发者得到更安全、更便宜、更容易维护的部署方式。

现代 SSG 框架还提供了混合渲染能力，让你在需要动态功能时不必推翻整个架构。所以问题不再是“要不要用 SSG”，而是“哪些页面适合预生成，哪些部分需要动态处理”。想清楚这一点，你就能用最小的运行时成本，构建出性能与体验俱佳的网站。

前端入门最大的陷阱，是一上来就学框架。JSX 怎么写、hooks 怎么用、路由怎么配，这些当然要会，但它们解决的是“在理解 Web 怎么运转之后，如何高效组织代码”的问题。跳过底层直接背框架 API，遇到白屏、水合失败、构建产物爆炸时，你手里没有可以推理的模型。

这篇文章按一条从底到上的路线走：先搞清楚浏览器和网络怎么工作，再写最朴素的 HTML，然后引入工具和框架，接着把服务器、CDN 这些部署设施拆开看，最后讲我自己的选择：Cloudflare Pages + Astro。

## 先建立心智模型：浏览器到底在干什么

写第一行前端代码之前，值得花几个小时搞清楚三件事：浏览器怎么把 HTML/CSS 画成像素，一次网络请求经历了什么，Node.js 为什么能让 JS 跑在服务器上。不需要读源码，但要有一张可以反复调用的粗粒度流程图。

浏览器拿到 HTML 后，走一条固定的流水线：解析 HTML 构建 DOM，解析 CSS 构建 CSSOM，匹配成渲染树，然后进入 **Layout（重排）** 计算每个盒子的位置和尺寸，**Paint（重绘）** 填充像素，最后 **Composite（合成）** 把各图层按顺序合并成最终画面——只有合成这一步在 GPU 上完成。这里的关键分界线是**合成层**：`transform` 和 `opacity` 属于合成器属性，浏览器会把应用了这两个属性的元素提升为独立图层，变化时只重新合成，完全跳过 Layout 和 Paint。这就解释了为什么用 `top`/`left` 做动画会触发重排、CPU 飙升，而用 `transform` 做位移能拿到硬件加速。另一个常见陷阱是**强制同步布局**：在 JS 里读取 `offsetTop` 或 `getBoundingClientRect()` 后立刻写样式，浏览器为了返回准确的读取值会强制立即执行 Layout，循环执行就形成“布局抖动”。

JS 引擎这边，入门只需要一个概念：**解释器 + JIT + 推测优化 + 去优化**。代码先被快速解释执行，跑热的函数会被编译成机器码；编译器会假设对象形状稳定、类型一致，猜对了就快，猜错了就退回解释执行——所以不会出错，只会变慢。知道这一点，你就明白为什么“保持数据结构稳定”“避免频繁改变变量类型”不是玄学。再往下深挖引擎内部，对入门阶段收益很低，先放着。

比引擎更该花时间的是**网络**。一次页面加载，浏览器要先做 DNS 解析、TCP/TLS 握手，然后发请求、收响应、解析 HTML，再发现 CSS/JS/图片，发起新一轮请求。这条链路里，你能控制的东西比想象中多：`Cache-Control` 决定浏览器和 CDN 怎么缓存，`preload`/`prefetch` 决定资源加载优先级，HTTP/2 的多路复用减少了连接开销，`defer`/`async` 决定脚本是否阻塞 HTML 解析。打开 Network 面板看一次真实页面的请求瀑布，比读十篇性能文章有用。

Node.js 是第三条线。很多人以为事件循环是 JS 引擎的一部分，其实不是：**引擎只负责执行 JS、管理堆和调用栈，调度异步 I/O 的是 libuv**，一个 C 写的跨平台库。libuv 的事件循环每一轮走过六个阶段——timers、pending callbacks、idle/prepare、poll、check、close callbacks。业务开发真正要盯住的是三个：**timers** 检查 `setTimeout`/`setInterval` 是否到期，**poll** 是重头戏，取出并执行 I/O 回调，**check** 执行 `setImmediate` 的回调。文件 I/O、DNS、crypto 这些操作系统没有提供非阻塞原语的操作，会被丢进 libuv 的线程池（默认 4 个线程）执行。所以你写的 `fs.readFile` 不阻塞主线程，不是因为 JS“快”，而是因为等待被移出了执行 JS 的那根线程。

最后是 **F12**。把 DevTools 当作你心智模型的外部探针，而不是一个“看看报错”的工具。入门阶段按这个顺序用：

**Elements** 看 DOM 树和 computed style，改样式看即时反馈。**Network** 刷新页面，按 Size 排序找出体积最大的 JS/CSS/图片，勾选 Priority 列看加载优先级，看 `Cache-Control` 是否生效。**Performance** 录一次交互，看主线程任务和渲染帧；录之前务必用**无痕窗口**并勾选 **Disable cache**，否则缓存和扩展会掩盖真实问题。Performance 面板顶部可以设 CPU 节流（如 4x slowdown）模拟中低端手机。**Application** 看 localStorage、Cookie、Cache Storage 和 Service Worker。**Sources** 打断点，看 source map。

你怀疑布局抖动，就去 Performance 里找 forced reflow；你怀疑 bundle 太大，就去 Network 里按体积排序。前端的调试能力，大半在这里。

## 从纯 HTML 开始，而不是从框架开始

建立完上面的模型，最该做的事是手写一个只有 HTML 和 CSS 的页面。不用构建工具，不用 npm，新建 `.html`，用 `<h1>`、`<p>`、`<a>`、`<img>` 和语义化标签把内容组织出来。然后用 CSS 做一件事：让页面在手机宽度下不横向滚动，在桌面宽度下有一点留白。

这一步的关键不是“学会 HTML 语法”，而是体会 **HTML 是结构和内容的载体，CSS 是呈现，JS 是在必要时才加入的行为**。一个只靠 HTML/CSS 就能读、能导航、能适配屏幕的页面，是前端最底层的确定性。后面无论什么框架，最终产物都要回到这个形态：浏览器收到的仍然是 HTML、CSS 和 JS。

有了这个手感之后，去接触博客生成器。**静态站点生成器（SSG）** 做的事情很朴素：你写 Markdown，它套上模板，在构建时生成一堆 HTML。不需要数据库，不需要运行时，`dist/` 直接扔给任何静态托管就能上线。它教会你两件贯穿后面所有内容的事：**内容与呈现分离**，以及**构建时和请求时的区分**。

2026 年入门阶段值得知道四个工具，各有各的定位：

**Hugo** 用 Go 写，单一可执行文件，构建速度是它的招牌——1000 页的站点中位数构建时间在 547ms 左右，远快于其他选手。适合主要写文章、不想碰 JS 工程化的人。

**Hexo** 基于 Node.js，中文资料和主题生态最厚，上手门槛最低，适合快速搭一个传统技术博客。

**Eleventy（11ty）** 是 JS 生态里最轻、最自由的选项，不强迫目录结构，支持多种模板引擎，适合想自己控制构建流程的人。

**Astro** 的定位是“内容驱动的现代框架”。它默认零客户端 JavaScript，在构建时把 `.astro` 组件渲染成静态 HTML；需要交互的地方用岛屿显式声明。它自带内容集合（Content Collections）做类型安全的 frontmatter 管理，学习成本比 Hugo/Hexo 稍高，但扩展性最强。

入门建议：如果你只想专注写作，从 **Hugo** 开始；如果你想以后把站点长成完整的内容网站，从 **Astro** 开始。选一个，把几篇 Markdown 变成静态页面，本地跑起来，观察生成出来的 HTML 长什么样。

## 框架不是起点，是规模化的答案

当页面多起来、组件需要复用、状态需要在视图之间同步时，纯 HTML + 手写 DOM 操作开始难以维护。这时框架才登场。

2026 年的格局很清楚：**React 依然是采用率最高的选择**，全球开发者采用率约 67%，招聘岗位最多；Vue 在中文社区和企业项目中根基深厚，语法更贴近原生，学习曲线最平缓；Svelte 以极小的运行时体积和编译时响应式在高性能场景中占有一席之地。

但真正需要分清的是 **UI 框架和全栈框架**。React、Vue、Svelte 本身解决的是组件和视图更新；**Next.js（React）、Nuxt（Vue）、SvelteKit（Svelte）** 是在它们之上的元框架，额外提供路由、SSR/SSG、API 路由和部署适配。入门阶段的正确顺序是：先把一个 UI 框架的组件、props、状态、副作用跑通，**不要一上来就同时学 UI 框架和它的元框架**。Next.js 的学习曲线明显比 React 本身更陡，因为它叠了路由系统、渲染模式、Server Components 等一整套概念。

更重要的是理解框架在帮你做什么。现代框架的核心工作可以概括为：把声明式的组件描述转换成对 DOM 的高效更新；在 SSR 场景下，先在服务器生成 HTML，到浏览器后再**水合**绑定事件。虚拟 DOM、编译时响应式、信号，都是实现这一目标的不同策略。你理解了渲染管线和网络请求，就能判断一个框架的取舍：它把成本放在了构建时、运行时还是传输时。

## 部署不是“最后一步”：服务器、CDN 与边缘

很多人把部署当成写完代码之后的上传动作。实际上，**你选择怎么部署，会反过来影响你该用什么工具、写什么代码**。

先把“服务器”这个词拆开。前端入门至少要分清四种：

**静态文件服务器** 只把 `dist/` 里的 HTML/CSS/JS 返回给浏览器。本地用 `npx serve dist`，生产上可以是 Nginx、对象存储或静态托管平台。这条链路上没有服务端逻辑，没有数据库连接，成本极低。

**传统常驻服务器** 是一台 VPS 或云服务器，跑 Nginx 做反向代理、HTTPS 和静态资源缓存，动态请求转发给后面的 Node.js/Java/Python 进程。你要懂端口、进程、日志、域名解析、证书续期。这是最“重”的一端。

**PaaS / 托管运行时**（Vercel、Netlify、Railway、Render）把构建、部署、HTTPS 和 CDN 打包好了，你只推代码。

**Serverless / 边缘函数**（Cloudflare Workers、AWS Lambda、Vercel Functions）没有常驻进程，按请求触发。你不用管服务器，但要接受运行时限制：冷启动、无本地文件系统、执行时长和内存上限。

判断标准很朴素：**内容型站点优先静态托管；需要登录、数据库、支付、复杂 API 时再上常驻服务器或 Serverless；需要低延迟鉴权、A/B、重写时考虑边缘函数。**

然后看 **CDN**。它不是“缓存一下静态文件”这么简单。一个请求从浏览器到源站，要经过三层缓存：浏览器私有缓存（受 `Cache-Control` 管）、边缘 PoP 的共享缓存、可选的源站盾（origin shield，把多个边缘的未命中合并成一次回源请求）。CDN 的设计可以收敛成三个耦合决策：**缓存键、TTL、失效方式**。

**缓存键**决定什么算“同一个资源”，也决定正确性。缓存键设计错了，用户可能看到别人的内容。**TTL** 决定成本和新鲜度的权衡：静态资源（带 hash 的 JS/CSS）用长 TTL 甚至 `immutable`，命中率拉到 95% 以上；HTML 用短 TTL 或不缓存。**失效**的优先级从高到低是：版本化 URL → `stale-while-revalidate` → surrogate-key 清除 → 路径清除 → 全清。带 hash 的静态资源天然免疫失效问题，因为内容变则 URL 变。

对于动态请求，CDN 可以做**动态加速**——不走缓存，但走优化过的回源链路，减少握手和路由开销。**边缘计算**则更进一步：在离用户最近的 PoP 上执行代码，做鉴权、重定向、个性化，不一定要回源。Cloudflare Workers 跑在轻量隔离运行时里，冷启动通常在 5ms 以内，代价是运行时不是完整 Node.js——没有 `fs`，不能用 `child_process`，只能使用 Web 标准接口。

所以现代前端的部署图景是一条分层光谱：**静态 + CDN → 边缘函数 → Serverless 函数 → 常驻服务器**。越往左越简单、越便宜、越快；越往右越灵活、越重。入门阶段应该尽可能从左端开始，只有需求确实推着你往右走时才移动。

## 我的选择：Cloudflare Pages + Astro

我自己的站点用 Cloudflare Pages 部署 Astro。这不是唯一正确的组合，但它很好地体现了“从左端开始、需要时再往右走一步”的思路。

Astro 的默认行为是 **零客户端 JavaScript**：`.astro` 组件在构建时渲染成静态 HTML，不往浏览器发送运行时。需要交互的地方，你用岛屿显式声明：把一个 React、Vue 或 Svelte 组件标记为 `client:load` 或 `client:visible`，Astro 只为这个组件加载对应的框架运行时，页面其余部分保持纯静态。这种部分水合的策略，让你不必在“全静态但不可交互”和“全量 SPA 但首屏沉重”之间二选一。

内容组织上，Astro 的内容集合用类型安全的 frontmatter 管理 Markdown/MDX，写博客的体验接近纯静态生成器，但你随时可以在同一个项目里混入 SSR 页面或 API 路由。它不强迫你放弃已经会用的 React 或 Vue 组件。

Cloudflare Pages 这边，静态 Astro 站点的部署几乎没有配置成本：连 Git 仓库，构建命令 `npm run build`，输出目录 `dist`，每次 push 自动触发构建和部署，自动 HTTPS，全球 CDN。如果需要 SSR，加上 `@astrojs/cloudflare` 适配器，Pages Functions 会在边缘运行渲染逻辑。需要 API 时，在 `functions/` 下写 Pages Functions，或者用 Astro 的 API 路由配合适配器。缓存策略也很清晰：带 hash 的静态资源长缓存，HTML 短缓存，边缘函数结果按需缓存。边界同样要记住：边缘运行时不是完整 Node.js，不能用 `fs`，要按 Web 标准写。

我推荐这个组合给入门者，原因不是它“新”，而是它**逼你做出正确的区分**：写内容时就是 Markdown 和静态 HTML，需要交互时才引入组件，需要服务端逻辑时才加适配器。你不会一开始就被 SSR、水合、缓存策略同时淹没。

## 一条可执行的四周路线

**第一周，不碰框架。** 手写三五个 HTML 页面，用语义化标签组织内容，CSS 做响应式布局。同时花一个下午读浏览器渲染流水线（DOM → CSSOM → Layout → Paint → Composite）和一次完整请求的链路（DNS → 握手 → 请求 → 响应 → 解析）。打开 F12，在 Network 面板按 Size 排序看一次真实页面的请求瀑布，在 Performance 面板用无痕窗口 + Disable cache 录一次加载。

**第二周，引入 JavaScript 和构建思维。** 在页面里加交互（点击、表单校验、`fetch` 一个公开 API）。装 Node.js，理解 `npm run build` 把一个源目录变成 `dist/` 的过程。选一个博客生成器（只想写作就 Hugo，想长成内容网站就 Astro），把几篇 Markdown 变成静态页面，本地预览，看生成的 HTML。

**第三周，选一个框架，但只用它做组件。** React 或 Vue 都行。把之前手写页面里的一个可复用部分改成组件，理解 props 和状态。不要急着上元框架和全局状态管理，先把“组件 = 接收输入、返回 UI 描述”做实。

**第四周，部署。** 把构建产物推到 GitHub，连上 Cloudflare Pages（或任何顺手的静态托管），配一个自定义域名。观察一次 push 触发的构建日志，打开线上页面的 Network 面板，对比本地和线上的加载差异。如果你用的是 Astro，尝试加一个 `client:visible` 的交互岛屿，看看多加载了多少 JavaScript。

之后的方向取决于你想深入哪里：想往后端走，补 Node.js 的事件循环六阶段、流和 HTTP；想往性能走，深挖渲染管线的合成层、Core Web Vitals 和打包分析；想往边缘走，学 Workers 的运行时约束和边缘存储。但无论往哪走，**浏览器怎么渲染、一次请求怎么走、东西部署在哪一层**这三样东西会一直有效。

前端入门真正的门槛，从来不是框架 API 的数量，而是你脑子里有没有一张从“浏览器解析一个 HTML 文件”到“用户在全球某个边缘节点看到像素”的完整地图。有了这张地图，工具换了，你只是换了一条路线走，不会迷路。
